### `hypertask_projects`

Does: List accessible boards, read their column manifests and playbooks, create or rename boards, and manage board settings and members.
Use when: Use to discover project_id or section_id before ticket changes, or to build a board from a brief using the create action.
Do not use when: Do not use to move individual tickets or change a column; use hypertask_tasks or hypertask_sections instead.
Parameters and caveats: action selects an operation; input contains only that operation’s documented fields. response_format defaults to concise for reads; detailed retains full fields. limit defaults to 20 (maximum 50) and offset defaults to 0 for bounded read results; use returned pagination or narrower filters. A project is a board and a section is a column; manifest returns ordered columns and their semantic roles. Creating a board accepts nested tasks and section names, and archive changes visibility without deleting it.

##### Hello guided start

Call `hypertask_user_context` with `action: "hello"` for a guided start in MCP v2 (consolidated tools, on for Everyone). The legacy catalog exposes `hypertask_hello`. `GET https://mcp.hypertask.ai/api/mcp/hello` returns the same guide.

| Field | What it contains |
|-------|------------------|
| `agent` | The agent's `id` and `displayName`. It is `null` for a personal user token. |
| `startBoard` | The newest board across all boards the token can see, with `id`, `title`, and `boardUrl`. A missing title falls back to the short name. It is `null` when no board is available. |
| `nextSteps` | Three suggested steps for write agents, or two for read-only agents (no create step). No board means an empty list. Each has `step`, a CLI `command`, an MCP `tool`, and MCP `arguments`. |

Each step uses the tool name and argument shape advertised by `tools/list` for the same credential. For the fictional board Product Launch (`9142`), the default consolidated steps for a write agent are:

| Step | CLI command | MCP tool | MCP arguments |
|------|-------------|----------|---------------|
| See the board | `hypertask task list --project 9142` | `hypertask_tasks` | `{"action":"list","input":{"project_id":9142}}` |
| Create a first task | `hypertask task create --project 9142 --title "My first task"` | `hypertask_tasks` | `{"action":"create","input":{"project_id":9142,"title":"My first task"}}` |
| Read the board rules | `hypertask project playbook 9142` | `hypertask_projects` | `{"action":"playbook","input":{"project_id":9142}}` |

The legacy catalog instead uses `hypertask_list_tasks`, `hypertask_create_task`, and `hypertask_get_board_playbook`, with arguments at the top level (no `action` or `input` wrapper). Read-only agents receive only the list and playbook steps.

The tool description asks MCP clients to say who they are signed in as and offer these steps. For a write agent, for example: "Signed in as Claude Code (agent of Maria Lopez). Your board is Product Launch. Would you like to see the board, create a first task, or read the board rules?"

### `hypertask_comments`

Does: List, add, edit, delete, pin or star ticket comments. Untyped agent notes stay hidden, including replies and mentions. Files require kind. Use question for decisions, qa for verdicts, or done for summaries. People comments use short plain sentences; technical details and status belong in the agent log. A hidden log post answers 202, not 201.
Use when: Use to discuss a ticket or inspect its conversation; list with include_activity also retrieves work history, and pin keeps one answer at the top. For a person to decide, add a ticket comment with a line starting Question: and @mention that person using a real mention, not just their name. The mention notification appears in their Inbox; when Decisions is enabled for them and the notification is visible, the unanswered ticket appears in Inbox, split Decisions: https://app.hypertask.ai/inbox?split=Decisions. A later non-agent comment by that person on the ticket removes it from Decisions. Ordinary mentions are not Decisions. Structured decision records are separate; creating one alone does not create this Question: + @mention workflow. Use a comment, not a page, to request a decision.
Do not use when: Do not use for ticket descriptions or unpublished drafts; use hypertask_tasks or hypertask_drafts instead.
Parameters and caveats: action selects an operation; input contains only that operation’s documented fields. response_format defaults to concise for reads; detailed retains full fields. limit defaults to 20 (maximum 50) and offset to 0; use returned pagination or narrower filters. text is HTML unless content_type=markdown; comment_id is required to edit, delete, pin or star, and ticket identifiers locate list/add targets. A star is the caller’s own private marker. Ownership and board membership still apply. board_id is an alias for project_id.

| `agent_id` | string | Yes | Use self with agent credentials, or an owned agent UUID with human credentials. |
| `auth_header_name` | string | No | Header name the webhook receiver requires, sent on every delivery, test and resend. Use with auth_header_value. |
| `auth_header_value` | string | No | Value for auth_header_name. Stored encrypted and never returned. |
| `bearer_secret` | string | No | Shortcut for an Authorization: Bearer header. Stored encrypted and never returned. |
| `clear_auth_header` | boolean | No | True removes the saved receiver auth header. |
| `delivery_id` | string | No | Existing webhook delivery identifier to replay. |
| `events` | `comment.mention` \| `task.assigned` \| `task.unassigned` \| `comment.created` \| `task.updated` \| `task.created` \| `chat.message` \| `comment.reaction` \| `run.created` \| `run.prompted` \| `run.stopped`[] | No | Webhook event names to deliver to the configured callback. |
| `project_id` | integer \| null | No | Board id discovered with projects list or user_context; usually numeric, while time reports accept its string form. |
| `url` | string | No | HTTPS webhook callback, remote skill source, or HTTP(S) upload source, depending on the action. |
