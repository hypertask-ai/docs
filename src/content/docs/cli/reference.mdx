The Hypertask CLI (`hypertask`) lets you manage tasks, projects, comments, and notifications directly from your terminal. It is the fastest way to interact with Hypertask programmatically and is the recommended interface for AI agents like Claude Code.

## Installation

```bash
npm install -g @hypertask/hypertask_cli
```

Verify the installation:

```bash
hypertask --version
```

<Aside type="tip">
**In-app shortcut:** Press `<kbd>Ctrl+K</kbd>` in Hypertask and search for **CLI** to open the CLI install dialog, which shows the install command and walks you through authentication without leaving the app. The dialog also links directly to the MCP token setup if you want to connect an AI agent at the same time.
</Aside>

<Aside type="caution">
The CLI package has moved to `<code>@hypertask/hypertask_cli</code>`. If you previously installed `<code>hypertask_cli</code>` (without the scope), uninstall it first: `<code>npm uninstall -g hypertask_cli</code>`
</Aside>

## Authentication

<Steps>

1. **Login via browser** (recommended):

   ```bash
   hypertask login
   ```

   This opens your browser to authenticate and saves the token locally. After the `<code>api.hypertask.ai</code>` cutover, the CLI always routes login requests through the new API endpoint to avoid 404s and ensure reliable authentication.

2. **Login with a token** (for CI/headless environments):

   ```bash
   hypertask login --token <your-jwt-token>
   ```

3. **Check your auth status:**

   ```bash
   hypertask status
   ```

4. **Logout:**

   ```bash
   hypertask logout
   ```

</Steps>

<Aside type="tip">
Pass `<code>--token <jwt></code>` on any command to override the saved token for that call. You can also pass `<code>--api-url</code>` to point at a custom API endpoint.
</Aside>

## Exit Codes and Error Behavior

The CLI uses exit codes so scripts and CI pipelines can reliably detect failures. Up to v1.8.0, some write commands exited with code 0 even when the write did not succeed, making errors invisible to callers. Starting from CLI 1.8.0, the CLI always fails loudly: every subcommand that encounters an error exits non-zero with an accompanying message.

<Aside type="caution">
Use `hypertask capabilities --json` in automation pipelines to discover whether a command supports JSON output without guessing, and rely on non-zero exit codes to detect failures.
</Aside>

### Exit Codes

| Code | Meaning |
|------|---------|
| `0` | Success |
| `1` | General runtime or API error (non-auth) |
| `4` | Authentication or authorization failure |
| `2` | Invalid usage — unknown or misspelled subcommand / missing required argument |

All subcommands that produce errors now exit with a dedicated code and either print to stdout or stderr. The CLI also monitors unhandled promise rejections and ensures they surface as non-zero exits.

### Transient Failures

Bot-challenge 403s, rate limits, and certain gateway errors are now retried automatically with exponential backoff instead of failing immediately. Starting from CLI 1.8.0:
- **Retried cases:** 403 (bot challenge), 408 (Request Timeout), 429 (Rate Limit), 500 (Internal Server Error), 502 (Bad Gateway), 503 (Service Unavailable), 504 (Gateway Timeout)
- **Backoff sequence:** retry attempts are spaced approximately 2 seconds, 10 seconds, and 30 seconds, then fail with a clear message
- **Error message phrasing:** `<code>transient challenge/rate limit — retry in a minute</code>` clarifies that the failure is temporary and not due to a bad token
- **Safe failures:** Writes are rejected before the mutation occurs, so retry cannot result in double-creation

**Not retried:** 500 and bare network errors are intentionally not retried to avoid re-processing a write that has already succeeded, which could cause duplicates or unexpected side effects.

### CLI API Routing

The CLI connects to the Hypertask API using a dedicated endpoint that is exempt from the Vercel bot challenge. Starting from CLI 1.5.0:
- **Default endpoint:** `https://api.hypertask.ai`
- **Routing:** CLI traffic is routed through `api.hypertask.ai`, not `app.hypertask.ai/v1` or other public-facing endpoints
- **Benefit:** Direct API access works reliably from VPS environments without intermittent 403s caused by bot-challenge checks

```bash
# CLI automatically connects to the exempt API endpoint
hypertask task get HTPR-2992
hypertask status
```

<Aside type="tip">
If you need to use a custom API URL (for self-hosted instances), you can override it via `<code>--api-url</code>`. This overrides the default routing and should not be required for standard Hypertask.
</Aside>

## `capabilities` / `commands`

Enumerate every command the CLI has, in one call — no recursive `--help` grepping needed.

The command has two modes, and which one you want depends on where the output is going:

```bash
hypertask capabilities          # ~145 lines of markdown, one line per command
hypertask capabilities --json   # the full tree, every command with every flag
```

**Paste the plain output into an agent's memory file.** Since CLI 1.13.7 the bare command prints a compact markdown list — command, arguments, one-line description — small enough to live in a `CLAUDE.md` permanently. The JSON tree is roughly 38 KB, which is why nobody ever pasted it anywhere.

`commands` is an alias for `capabilities`; both are identical.

| Flag | Description |
|------|-------------|
| `--json` | Output as JSON (recommended for programmatic use) |

**Sample output (abbreviated):**

```json
[
  {
    "name": "task create",
    "description": "Create a new task",
    "options": [
      { "flags": "--project <id>",        "description": "Project ID (required)" },
      { "flags": "--title <text>",         "description": "Task title (required)" },
      { "flags": "--attach <path-or-url>", "description": "Attach a local file or URL (repeatable)" }
    ]
  },
  {
    "name": "task get",
    "description": "Get full details of a task. Plain output is complete, tab-separated, and safe to parse without --json.",
    "options": []
  },
  {
    "name": "comment list",
    "description": "List comments on a task. Plain output is complete, tab-separated, and safe to parse without --json.",
    "options": []
  }
]
```

<Aside type="tip">
**For AI agents:** `hypertask capabilities --json` is the recommended starting point for any agent that drives the CLI. All three locations where `--attach` is supported — `task create`, `task update`, and `comment add` — appear explicitly in the output. Read commands like `task get` and `comment list` also advertise in the capabilities dump that their plain output is complete and tab-separated, so agents do not need to default to `--json` + custom parsers for these commands.
</Aside>

## Tasks

### `task list`

List tasks with filters.

```bash
hypertask task list --project 15 --section "Doing" --assigned-to me
```

| Flag | Description | Default |
|------|-------------|---------|
| `--project <id>` | Filter by project ID | — |
| `--section <name>` | Filter by section name | — |
| `--assigned-to <value>` | Filter by assignee: `me`, `unassigned`, or a user ID | — |
| `--created-by <id>` | Filter by creator user ID (numeric) | — |
| `--priority <list>` | Comma-separated priorities: `urgent`, `high`, `medium`, `low` | — |
| `--sort-by <field>` | Sort results by `createdAt`, `updatedAt`, or `dueDate` | — |
| `--sort-order <asc\|desc>` | Sort direction — use together with `--sort-by` | — |
| `--limit <n>` | Results per page | `10` |
| `--offset <n>` | Pagination offset | `0` |

<Aside type="note">
**File attachments** are not on `task list` — use `task create --attach` or `task update --attach` to attach files. See the [Capability Discovery](#capability-discovery) section or run `hypertask capabilities --json` to see all commands that support `--attach`.
</Aside>

<Aside type="note">
**`--json` output includes uniqueIndex:** When using `--json`, each task row includes a `uniqueIndex` field. This is derived from the ticket number for tasks where the API omits the index, ensuring reliable parsing with `json.load`.
</Aside>

### `task get` / `task show`

Get full details of a single task by its ticket number. Response always includes the complete task description (including long, multi-paragraph descriptions), labels, `parent_id` for subtasks, and the task URL.

```bash
hypertask task get HTPR-2992
hypertask task show HTPR-2992   # alias for task get
```

| Argument | Description |
|----------|-------------|
| `<ticket>` | Ticket identifier in PREFIX-NNN format (e.g., `HTPR-2992`) |

<Aside type="tip">
**Plain output is complete.** The default (non-`--json`) output of `task get` is tab-separated and contains every field — you do not need `--json` just to get the full task data. This is stated in the command's `--help` output and in `hypertask capabilities --json`. Use `--json` when you need structured output for tools like `jq`.

`task show` is an alias for `task get` — both commands are identical.
</Aside>

### `task tree`

Show the full parent/subtask hierarchy for a task. Displays the family tree of a task including all parents and children.

```bash
hypertask task tree --ticket HTPR-2992
```

| Flag | Description | Default |
|------|-------------|---------|
| `--ticket <ticket>` | Ticket number (e.g., `HTPR-2992`) | — |
| `--task-id <id>` | Numeric task ID | — |
| `--depth <n>` | Max levels deep to show | Full tree |

```bash
# Show subtask tree by ticket number
hypertask task tree --ticket HTPR-2992

# Show subtask tree by task ID, limited to 2 levels deep
hypertask task tree --task-id 1234 --depth 2
```

### `task create`

Create a new task.

```bash
hypertask task create \
  --project 15 \
  --title "Implement dark mode toggle" \
  --description "<p>Add a toggle switch in the settings panel to switch between light and dark themes.</p>" \
  --priority high \
  --labels "frontend,UX" \
  --estimate 3 \
  --due 2026-04-01
```

| Flag | Description |
|------|-------------|
| `--project <id>` | Project ID (required) |
| `--title <text>` | Task title (required) |
| `--description <text>` | Description (HTML preferred; see note below) |
| `--priority <p>` | Priority: `urgent`, `high`, `medium`, `low`, `none` |
| `--estimate <n>` | Size index: `0` = none, `2`–`6` = XS, S, M, L, XL |
| `--labels <list>` | Comma-separated label names or IDs (e.g., `"CLI,BUG"`) |
| `--due <date>` | Due date in ISO 8601 format (e.g., `2026-04-01`) |
| `--parent-task <id>` | Parent task ID — creates this task as a subtask |
| `--section <id\|name>` | Section ID or name (e.g., `4005` or `"Doing"`) |
| `--assignee <list>` | Comma-separated user IDs to assign (e.g., `"42"` or `"42,99"`) |
| `--attach <path-or-url>` | Attach a local file or URL (repeatable for multiple attachments) |

<Aside type="note">
**Description format:** HTML is the canonical format — wrap text in `<p>` tags and use standard HTML elements like `<ul>`, `<ol>`, `<code>`, and `<strong>`. Plain text without HTML tags is auto-wrapped in `<p>...</p>` before being sent to the API. Rich structured text using markdown-style headers and numbered steps (a "bug template" style) is also accepted and stored correctly.
</Aside>

<Aside type="caution">
**Parent task validation:** `<code>--parent-task</code>` must be a positive integer. Passing a non-numeric value or a value that doesn't correspond to an existing task results in a clear error before the API call. The task is not created if parent validation fails.
</Aside>

<Aside type="note">
**`--attach` is non-atomic.** The task is created first, and the attachment upload runs as a separate step immediately after. If the upload fails (e.g. unsupported file type, network error), the CLI reports which task was created, explains why the attachment failed, prints the exact retry command, and exits with a dedicated error code — so you always know the task exists and can re-attach without creating a duplicate. Example:
```
Created task HTPR-3102: Review mockups
Attachment failed: unsupported content type text/html
  Retry: hypertask task update HTPR-3102 --attach ./mockup.png
```
</Aside>

```bash
# Create a subtask under an existing task
hypertask task create \
  --project 15 \
  --title "Design the toggle component" \
  --parent-task 1234 \
  --priority medium

# Create a task with file attachments
hypertask task create \
  --project 15 \
  --title "Review mockups" \
  --attach ./mockup.png \
  --attach https://example.com/spec.pdf
```

<Aside type="note">
**JSON output control:** When using `<code>--json</code>`, `<code>task create</code>` emits exactly one JSON document containing the created task. Human-readable success messages are hidden behind `<code>--json</code>` (the success block is gated behind `<code>--json</code>` with an early return). The typical output pattern after a successful creation is: `<code>{"id":1234,"ticketNumber":"HTPR-3304","title":"...","status":"Normal"}</code>`.
</Aside>

### `task update`

Update an existing task's properties.

```bash
hypertask task update HTPR-2992 --priority urgent --due 2026-03-25
```

| Flag | Description |
|------|-------------|
| `--title <text>` | New title |
| `--description <text>` | New description (plain text or HTML; plain text is auto-wrapped in `<p>` tags) |
| `--priority <p>` | New priority |
| `--estimate <n>` | Size index: `0` = none, `2`–`6` = XS, S, M, L, XL |
| `--due <date>` | New due date (ISO 8601) |
| `--clear-due` | Remove the due date (e.g., to clear a past due date) |
| `--status <s>` | Lifecycle status: `Normal`, `Archive`, or `Deleted` |
| `--section <id\|name>` | Section (board column): ID or name like `"Doing"`, `"Done"` |
| `--project <id>` | Project ID (required when using `--section` with a name across projects) |
| `--assignee <list>` | Comma-separated user IDs to assign (e.g., `"42"` or `"42,99"`) |
| `--labels <list>` | Comma-separated label names or IDs |
| `--parent-task <id>` | Re-parent: set a new parent task by numeric ID |
| `--clear-parent` | Detach this task from its current parent, making it a top-level task |
| `--attach <path>` | Attach a local file (repeatable) |

<Aside type="note">
**Status vs. Section:** These are two different concepts. Use `--status` for the task lifecycle (active, archived, or deleted). Use `--section` to move a task between board columns (e.g., from "Backlog" to "Doing"). The `--status` flag only accepts `Normal`, `Archive`, or `Deleted` — not section names.
</Aside>

<Aside type="note">
**Parent task validation:** `<code>--parent-task</code>` must be a positive integer. Passing a value that doesn't correspond to an existing task results in a clear error before the API call. If `--parent-task` is zero or negative, or not a valid integer, the task is not updated.
</Aside>

```bash
# Move a task to the "Doing" section
hypertask task update HTPR-2992 --section "Doing"

# Archive a completed task
hypertask task update HTPR-2992 --status Archive

# Update labels
hypertask task update HTPR-2992 --labels "CLI,reviewed"

# Re-parent a task (make it a subtask of another task)
hypertask task update HTPR-2992 --parent-task 1234

# Detach a subtask from its parent (make it a top-level task)
hypertask task update HTPR-2992 --clear-parent

# Clear a task's due date
hypertask task update HTPR-2992 --clear-due
```

<Aside type="tip">
**Detaching subtasks:** Use `--clear-parent` to remove a task's parent and promote it to a standalone top-level task. This is distinct from `--parent-task`, which sets or changes the parent. The `--clear-parent` flag works both from the CLI and via the MCP `hypertask_update_task` tool (pass `parent_task_id: null`).
</Aside>

### `task move`

Move a task to a different section within the same board, or to a different project entirely.

```bash
# Move within the same board
hypertask task move HTPR-2992 --section "Done"

# Move to a different project
hypertask task move HTPR-2992 --to 20 --to-section 5010
```

| Flag | Description |
|------|-------------|
| `--section <name>` | Destination section name within the same board (e.g., `"Doing"`, `"Done"`) |
| `--to <id>` | Target project ID — move to a different project |
| `--to-section <id>` | Target section ID in the destination project (use with `--to`) |

### `task move-board` / `task move-project`

Move a task to a different project/board entirely. Alias: `task move-board` (preferred) and `task move-project` (legacy).

```bash
hypertask task move-board HTPR-2992 --target-project 20 --target-section 5010
hypertask task move-project HTPR-2992 --target-project 20 --target-section 5010
```

| Flag | Description |
|------|-------------|
| `--target-project <id>` | Target project ID |
| `--target-section <id>` | Target section ID |

### `task move-to-inbox`

Move a task into a specific user's inbox. This is useful when an agent (or another process) creates tasks on a user's behalf and needs to surface them in that user's notifications without relying on self-assignments or direct assignment.

```bash
hypertask task move-to-inbox HTPR-2992 --user 42
```

| Flag | Description |
|------|-------------|
| `--user <id>` | Recipient user ID (must be a member of the task's project) |

<Aside type="tip">
Use this when an agent or external service needs to funnel a task into a specific human's inbox for visibility without self-notification triggers that skip due to being an "own-action" record.
</Aside>

**Why not self-assign?** Self-assignment and self-mention do not trigger notifications, because Hypertask never notifies you about your own actions. With `--user`, the task is moved into the recipient's inbox as a separate notification, ensuring the human notices the new task.

<Aside type="caution">
The recipient must be a member of the task's project. Attempting to move a task into another user's inbox will fail with a 400 if they lack project access.
</Aside>

**Common use case — Slack-to-Hypertask draft bots**

When your team uses Slack and a bot drafts Hypertask tasks for people, use `move-to-inbox` in the bot's workflow:

```bash
# 1. Create a task via Slack
hypertask task create \
  --project 15 \
  --title "Review the Q3 design proposal" \
  --description "<p>Share the deck and gather feedback.</p>" \
  --priority high

# 2. Identify the intended recipient (e.g., via user ID from Slack user lookup)
# Suppose the intended assignee is team member with ID 42
hypertask task move-to-inbox HTPR-XXXXX --user 42
```

This ensures the task appears in the recipient's inbox regardless of whether they are a member of the board or project, and without triggering a self-assignment notification that would skip.

### `task list-custom-field`

List the custom fields defined on the current board, including their IDs, names, and types. This command mirrors the REST surface seen in the API and helps scripts discover available typed data attached to tasks.

```bash
hypertask task list-custom-field --project 123
```

| Flag | Description |
|------|-------------|
| `--project <id>` | Project whose board's custom fields to list (required) |

**Expected output (text-tab-separated):**

```
fieldId	name			type
789	ICE			number
790	Sprint		select
```

Relations: you can pipe this output into `jq` for filtering, or use it to dynamically derive field IDs and types for subsequent CLI invocations like `task update-custom-field`.

### `task update-custom-field`

Set or clear a custom field value on an existing task. This lets scripts and agents modify typed task metadata (e.g., ICE scores, sprint tags, dates) from the terminal with validation already enforced by the server.

```bash
hypertask task update-custom-field HTPR-2992 --field-id 789 --value 42
hypertask task update-custom-field HTPR-2992 --field-name ICE --value 8
hypertask task update-custom-field HTPR-2992 --field-id 790 --value "K5"
hypertask task update-custom-field HTPR-2992 --field-id 790 --clear
```

| Flag | Description |
|------|-------------|
| `<ticket>` | The task's ticket number (e.g., `HTPR-2992`) |
| `--field-id <id>` | The field's numeric ID — use after retrieving it via `list-custom-field` |
| `--field-name <name>` | The field's string name — server will try the current board and project context; for cross-project callers, use `--field-id` |
| `--value <val>` | A value matching the field type (number, string, ISO date, boolean) |
| `--clear` | Remove the value instead of setting it |

**Examples:**

```bash
# Set a number field (ICE score)
hypertask task update-custom-field HTPR-2992 --field-name ICE --value 42

# Set a date field
hypertask task update-custom-field HTPR-2992 --field-name "Sprint Start" --value "2026-09-01"

# Clear a value
hypertask task update-custom-field HTPR-2992 --field-id 789 --clear
```

## Views

Views are named filter/sort configurations saved in the Hypertask UI (e.g. "Dev Review & QA", "Tests Running"). The CLI exposes read-only commands to list views and fetch their pre-filtered tasks — especially useful for agents working on large boards where scanning all tasks would be noisy and slow.

### `view list`

List all saved views for a project, including each view's ID, title, and visibility.

```bash
hypertask view list --project 15
```

| Flag | Description |
|------|-------------|
| `--project <id>` | Project ID (required) |

**Example output:**

```
ID             NAME                  VISIBILITY
view_abc123    Dev Review & QA       shared
view_def456    Tests Running         shared
view_ghi789    My Open Tasks         private
```

### `view get`

Fetch tasks from a specific saved view, with that view's filters already applied.

```bash
hypertask view get view_abc123
```

| Argument | Description |
|----------|-------------|
| `<view-id>` | The view identifier (from `view list`) |

| Flag | Description | Default |
|------|-------------|---------|
| `--limit <n>` | Max tasks to return | `50` |
| `--offset <n>` | Pagination offset | `0` |

```bash
# Discover views, then pull tasks from one
hypertask view list --project 15
hypertask view get view_abc123 --limit 20

# Use JSON output for scripting
hypertask view get view_abc123 --json | jq '.[].title'
```

<Aside type="tip">
**For AI agents on large boards:** start with `hypertask view list` to discover saved views, then `hypertask view get` to pull a focused, pre-filtered set of tasks. This is significantly faster and cheaper in tokens than listing all tasks and filtering client-side.
</Aside>

## Search

### `search`

Search for tasks by keyword. Results display full ticket titles (wrapping long titles across multiple lines in the table so nothing is cut off), links to each task, and include a **Due** column showing due dates where available.

```bash
hypertask search "dark mode" --project 15 --limit 5
```

| Argument / Flag | Description | Default |
|-----------------|-------------|---------|
| `<query>` | Search query (required) | — |
| `--project <id>` | Restrict search to a project | — |
| `--limit <n>` | Maximum results | `10` |
| `--json` | Output raw JSON instead of the formatted table | — |

<Aside type="tip">
This command is an alias under `tasks search` as of CLI 1.9.1. Using `tasks search` for convenience works the same as the top-level `search` command.
</Aside>

### `tasks search`

## Comments

### `comment list`

List all comments on a task, including the full body of each comment.

```bash
hypertask comment list HTPR-2992
```

| Argument | Description |
|----------|-------------|
| `<ticket>` | Ticket identifier in PREFIX-NNN format (e.g., `HTPR-2992`) |

<Aside type="tip">
**Plain output is complete.** The default (non-`--json`) output of `comment list` is tab-separated and contains every comment field — author, timestamp, and full text. You do not need `--json` to get all the data. This is stated in the command's `--help` output and in `hypertask capabilities --json`. Use `--json` when you need structured data for downstream tools.
</Aside>

### `comment add`

Add a comment to a task. The comment is persisted immediately and a real comment URL is returned — use `comment list` to confirm the comment appears.

```bash
hypertask comment add HTPR-2992 --text "<p>Looks good, merging now.</p>"
```

| Flag | Description |
|------|-------------|
| `--text <text>` | Comment text (HTML format) |
| `--attach <path-or-url>` | Attach a local file or URL to the comment (repeatable for multiple attachments) |
| `--improve` | Run `--text` through an AI rewrite (see [`ai improve`](#ai-improve)) before posting |
| `--improve-command <name>` | Which rewrite to run with `--improve`: `improve-readability` (default), `fix-spelling`, `summarize`, `make-shorter`, or `translate:<language>` |

```bash

hypertask comment add HTPR-2992 --text "<p>ya this looks good, ill merge it now</p>" --improve
```

The project used for the rewrite is resolved from the ticket, so `--project` is not needed here.

<Aside type="note">
**`tasks search` provides a convenient alias under a task-aggregated command group.** If you prefer to cluster subcommands relating to tasks, `tasks search` works the same as the top-level `search` command.

```

```

Both forms are valid and documented for clarity in task-accessible commands.
</Aside>

```bash

hypertask comment add HTPR-2992 \
  --text "<p>Screenshot of the issue attached.</p>" \
  --attach ./screenshot.png
```

```bash

```
</Aside>

<Aside type="note">
**`--json` output control:** When using `--json`, `comment add` emits exactly one JSON document containing the full comment details. Human-readable confirmation is hidden through a controlled early return, and the typical output structure is accessible for programmatic parsing.
</Aside>

## Drafts

A draft is unsent text parked on a task: a comment you have not posted yet, or a replacement description you have not applied yet. Each user gets **one comment draft and one description draft per task**.

<Aside type="tip">
**Drafts you create here show up in the web app.** Open the task in Hypertask and the comment draft is already sitting in the composer, ready for the person to read, edit, and send. This is how you hand a human something to approve instead of posting on their behalf.
</Aside>

### `draft create`

Create a draft on a task. Without `--comment` you are drafting the **description**.

```bash
# Comment draft — lands in the task's comment composer
hypertask draft create HTPR-2992 --comment --text "Ready for review, tests are green."

# Description draft — replaces the description when published
hypertask draft create HTPR-2992 --text "Rewrite the importer to stream rows."
```

| Argument / Flag | Description |
|-----------------|-------------|
| `<ticket>` | Ticket identifier in PREFIX-NNN format |
| `--text <text>` | Draft text (plain text or markdown, converted to HTML) |
| `--comment` | Draft a comment; omit to draft the description |

Creating a draft when one already exists **overwrites it** rather than adding a second one. The command still prints "Created".

### `draft list`

Show the drafts on a task, with their IDs.

```bash
hypertask draft list HTPR-2992
```

Empty drafts are not returned — a draft whose content is blank reads as no draft at all.

### `draft update`

Replace a draft's text, by draft ID.

```bash
hypertask draft update 98711 --text "Ready for review. One follow-up filed."
```

### `draft publish`

Turn the draft into the real thing: a comment draft is posted as a comment, a description draft replaces the task description. The draft is consumed.

```bash
hypertask draft publish 98711
```

### `draft delete`

Discard a draft without publishing it.

```bash
hypertask draft delete 98711
```

## AI

Both `ai` subcommands run the same AI harness the web editor uses — board context, the team's configured model, and any custom AI instructions set for the project. They count against the team's AI usage like the in-app helpers, and return a 403 if the team has AI writing switched off in its settings.

### `ai write`

Draft a task description or a comment with AI. Without `--apply` it prints the draft and changes nothing.

```bash
# See what it would write (task-writer is the default mode)
hypertask ai write "Explain the rollback plan" --task HTPR-4650

# Write the result back to the task
hypertask ai write "Tighten this description" --task HTPR-4650 --apply

# Draft a comment instead, using the same harness as "Write with AI" in the editor
hypertask ai write "Summarize the decision above" --task HTPR-4650 --mode write-with-ai --apply
```

| Argument / Flag | Description |
|-----------------|-------------|
| `<prompt>` | What you want written. Supports `/slug` skill invocation, same as the editor's slash-command popup |
| `--task <ticket>` | Ticket used as context, e.g. `HTPR-4650` |
| `--project <id>` | Board to use, defaults to the task's board |
| `--mode <task-writer\|write-with-ai>` | `task-writer` (default) drafts a task description. `write-with-ai` drafts a comment |
| `--instructions <text>` | Extra instructions for this run |
| `--apply` | Apply the result. In `task-writer` mode this writes description, title, priority, and size back to the ticket. In `write-with-ai` mode this posts the draft as a comment. Requires `--task` |

<Aside type="note">
`ai write` calls `POST /api/mcp/ai/task-writer` under the hood.
</Aside>

### `ai improve`

Run one of the editor's forward-slash text rewrites (the same commands behind **Rewrite**, **Summarize**, and **Fix Spelling & Grammar** in the app) from the terminal, without touching any ticket.

```bash
# Improve readability of a string (improve-readability is the default command)
hypertask ai improve "we should of shipped this last week honestly" --project 15

# Pipe text in instead of passing it as an argument
echo "the button dont work when u click twice fast" | hypertask ai improve --task HTPR-1234 --command fix-spelling

# Translate
hypertask ai improve "Ship it Friday." --project 15 --command translate:german
```

| Argument / Flag | Description |
|-----------------|-------------|
| `<text>` | Text to rewrite. Omit this and pipe text on stdin instead |
| `--task <ticket>` | Ticket to resolve the project (and its AI settings/model) from |
| `--project <id>` | Project whose AI settings and model to use. One of `--task` or `--project` is required |
| `--command <name>` | `improve-readability` (default), `fix-spelling`, `summarize`, `make-shorter`, or `translate:<language>` (e.g. `translate:german`, `translate:brazilian portuguese`) |
| `--json` | Print the full API response instead of just the rewritten text |

<Aside type="tip">
**Output format depends on how you run it.** In an interactive terminal, `ai improve` prints plain text. When output is piped or redirected, it prints the raw HTML instead, so you can capture it and feed it into another command that expects HTML (e.g. `comment add --text` or `task update --description`).

```bash
REWRITTEN=$(hypertask ai improve "fix this up" --task HTPR-1234)
hypertask comment add HTPR-1234 --text "$REWRITTEN"
```
</Aside>

<Aside type="note">
`ai improve` calls `POST /api/mcp/ai/improve`, a sibling of `POST /api/mcp/ai/task-writer`. Bearer-authenticated, body `{ "project_id": 15, "text": "...", "command": "fix-spelling" }` (`command` optional, defaults to `improve-readability`), response `{ "success": true, "html": "...", "command": "fix-spelling", "model": "..." }`. `project_id` is required because it carries the team's AI settings and model choice — that's why `ai improve` needs `--project` or `--task`.
</Aside>

## Management Keys

Management keys (`htmk_…`) administer your account rather than read your boards. Since CLI 1.13.9 you can manage them from the terminal.

```bash
hypertask admin keys list
hypertask admin keys create --name "ci-runner"
hypertask admin keys create --name "ci-runner" --scope full --expires-in-days 90
hypertask admin keys revoke 12
```

**A created key is printed once and never again.** Store it before the command scrolls away.

| Flag | Description |
|------|-------------|
| `--name <name>` | Key name, 1–32 characters (required for `create`) |
| `--scope <scope>` | `management` (default) or `full` |
| `--expires-in-days <n>` | 1–365; omit for a key that never expires |
| `--management-key <key>` | Authenticate with this key instead of your session |

A key cannot create another key with wider permissions than it holds; attempting it fails with `insufficient_scope`.

**Where the key comes from**, in order: `--management-key`, then the `HYPERTASK_MANAGEMENT_KEY` environment variable, then one saved with `hypertask token set-management-key <key>`, then your logged-in session. The agent commands (`agents create`, `agents revoke`, `agents rotate-token`) resolve it the same way.

## Common Workflows

### Pick up a task from your inbox

```bash
# 1. Check notifications
hypertask inbox list

# 2. Read the task details (full description included; plain output is complete)
hypertask task get HTPR-2992
# or use the alias
hypertask task show HTPR-2992

# 3. Move it to "Doing"
hypertask task move HTPR-2992 --section "Doing"

# 4. Archive the notification
hypertask inbox archive 101
```

### Create and assign a task

```bash
# 1. Find the project and its members
hypertask project list
hypertask project members 15

# 2. Create the task
hypertask task create \
  --project 15 \
  --title "Fix login timeout issue" \
  --description "<p>Users are getting logged out after 5 minutes of inactivity. Expected session length is 24 hours.</p>" \
  --priority urgent \
  --labels "bug,auth"

# 3. Assign it (use the user ID from project members)
hypertask task assign HTPR-3050 --user 42
```

### Invite a team member to a project

```bash
# 1. Invite them by email
hypertask project invite 15 --email newmember@example.com

# 2. Confirm they appear in the member list (once they accept)
hypertask project members 15
```

### Manage board sections

```bash
# List existing sections and their IDs
hypertask section list --project 15

# Add a new section
hypertask section create --project 15 --title "In Review"

# Rename a section
hypertask section rename --project 15 --section "In Review" --title "Code Review"

# Reorder: move "Code Review" to appear after "Doing"
hypertask section reorder --project 15 --section "Code Review" --after "Doing"

# Remove a section
hypertask section delete --project 15 --section "Code Review"
```

### Manage subtask relationships

```bash
# Create a task as a subtask of an existing task
hypertask task create \
  --project 15 \
  --title "Write unit tests for auth module" \
  --parent-task 1234

# Re-parent an existing task under a different parent
hypertask task update HTPR-2992 --parent-task 5678

# Promote a subtask to a top-level task (detach from its parent)
hypertask task update HTPR-2992 --clear-parent

# Inspect the full subtask hierarchy
hypertask task tree --ticket HTPR-1234
```

### Triage tasks by priority

```bash
# List all urgent and high-priority tasks
hypertask task list --project 15 --priority urgent,high

# Review unassigned tasks
hypertask task list --project 15 --assigned-to unassigned

# Search for something specific
hypertask tasks search "payment" --project 15
```

### Work from a saved view (recommended for large boards)

```bash
# 1. Discover available views (includes visibility)
hypertask view list --project 15

# 2. Pull tasks from a focused view
hypertask view get view_abc123

# 3. Work the task as normal
hypertask task get HTPR-2992
hypertask task move HTPR-2992 --section "Doing"
hypertask comment add HTPR-2992 --text "<p>Starting work on this now.</p>"
```

### Create and manage views

```bash
# Create a new view
hypertask view create \
  --name "High priority in Doing" \
  --project 15 \
  --section "Doing" \
  --priority "high,urgent" \
  --sort-by "dueDate" \
  --sort-order "asc"

# Switch to a view
hypertask view switch view_abc123

# Update view filters and sort
hypertask view update view_abc123 \
  --section "Doing,In Review" \
  --priority "high" \
  --sort-by "createdAt" \
  --sort-order "desc"

# Delete a view
hypertask view delete view_abc123
```

### Complete a task

```bash
# 1. Add a final comment (plain @mention works)
hypertask comment add HTPR-2992 --text "<p>Deployed to production. Verified working. @Alice please close this out.</p>"

# 2. Move to Done
hypertask task move HTPR-2992 --section "Done"
```

### Attach files to a task or comment

```bash
# Attach files when creating a task
hypertask task create \
  --project 15 \
  --title "Review design assets" \
  --attach ./wireframe.pdf \
  --attach ./mockup.png

# Attach a file to an existing task
hypertask task update HTPR-2992 --attach ./final-spec.pdf
```

### Discover all CLI capabilities (for agents)

```bash
# Dump the full command + option tree as JSON
hypertask capabilities --json

# Pipe to jq to find every command that supports --attach
hypertask capabilities --json | jq '[.[] | select(.options[]?.flags | contains("--attach"))]'

# Identify read commands — their plain output is complete and tab-separated
hypertask capabilities --json | jq '[.[] | select(.description | contains("tab-separated"))]'
```

### Use JSON output for scripting

```bash
# Pipe task data to jq
hypertask task list --project 15 --json | jq '.[].title'

# Get a task's priority
hypertask task get HTPR-2992 --json | jq '.priority'

# Search and process results
hypertask tasks search "dark mode" --project 15 --json | jq '.[].ticketNumber'

# For simple reads, plain output is sufficient
hypertask task get HTPR-2992
hypertask comment list HTPR-2992
```
