The native Hypertask CLI lets you manage tasks, projects, comments, and notifications from your terminal. The executable is named `hypertask`. The CLI ships as a native Zig binary (htz) and can also be installed via npm.

## Install

### Via npm (recommended)

```bash
npm install -g @hypertask/hypertask_cli@latest
```

This installs a lightweight npm shim that fetches and runs the official htz binary for your platform, ensuring you always have the latest version.

### Via curl (Linux / macOS)

On Linux or macOS, run:

```bash
curl -fsSL https://raw.githubusercontent.com/hypertask-ai/cli/8a9245246cec8ddac4ab1dfccae5c5cba5c39707/scripts/install.sh | sh
hypertask --version
```

The installer detects x64 or ARM64, downloads the matching binary from the latest [GitHub release](https://github.com/hypertask-ai/cli/releases), and verifies its SHA-256 checksum. It installs to `~/.local/bin` by default. Set `HYPERTASK_INSTALL_DIR` to choose another directory.

### Via PowerShell (Windows x64)

On Windows x64, download the native executable with PowerShell:

```powershell
Invoke-WebRequest https://github.com/hypertask-ai/cli/releases/latest/download/hypertask-windows-x86_64.exe -OutFile hypertask.exe
.\hypertask.exe --version
```

Move `hypertask.exe` to a directory on your `PATH` to run it from any terminal.

### Fleet auto-install behavior

When you merge a commit into the hypertask-ai/cli repository, the VPS fleet runs an automated install workflow:

- The trusted runner builds the htz binary in ReleaseFast mode.
- It preserves any existing symlinks under `~/.local/bin`.
- It only considers the install successful after verifying the installed binary matches the freshly built commit.
- Previous verifications and log metadata are retained to detect drift or mismatches.

If an install does not succeed, the CI/CD pipeline fails and prevents the commit from being considered merged.

## Inside the Hypertask App

When you choose to install Hypertask from the web app, the in-app installer (CLI install dialog) uses the npm shim to fetch the htz binary for you. This keeps the command identical across all install channels.

## Migrate from the Node CLI

We've shipped the native htz CLI and published an npm shim so you can install it the same way you did before:

```bash
npm install -g @hypertask/hypertask_cli@latest
```

Remove the old npm package before installing so its global shim cannot hide the native binary:

```bash
npm uninstall -g @hypertask/hypertask_cli
npm install -g @hypertask/hypertask_cli@latest
```

Most commands and flags stay the same. The native CLI also accepts direct top-level section commands such as `hypertask section create`.

## Comments commands

### hypertask comment add

Post a comment to a ticket from the terminal.

```bash
hypertask comment add <ticket_number> --text "<comment text>"
```

**Behavior:**

- Adds a new comment to the specified ticket.
- The `--text` flag holds your comment content; keep it short so it renders cleanly.
- Requires authentication via API key or session cookie.

```bash
hypertask comment add 12345 --text "Task should complete by EOD"
```

### hypertask comment list

List comments for a ticket from the terminal.

```bash
hypertask comment list <ticket_number>
```

**Behavior:**

- Returns a human-readable list of comments for the given ticket.
- The output includes comment content, timestamps, and author information.
- Requires authentication.

```bash
hypertask comment list 12345
```

## Task details commands

### hypertask task get

Display details for a task from the terminal.

```bash
hypertask task get <ticket_number>
```

**Behavior:**

- Returns full task details including fields, assignees, sections, and history.
- Useful for inspecting tasks before updating or acting on them.
- Requires authentication.

```bash
hypertask task get 12345
```

### hypertask task update

Update a task from the terminal.

```bash
hypertask task update <ticket_number> --field "<field>" --value "<value>"
```

**Behavior:**

- Updates a task field without revisiting the web app.
- Supports fields like `title`, `description`, `priority`, `assignee`, and `section`.
- Requires authentication.

```bash
hypertask task update 12345 --field "priority" --value "high"
hypertask task update 12345 --field "assignee" --value "user@example.com"
```

<Aside type="note">The `comment add` and `comment list` commands were previously available only on the Zig CLI. The Node CLI now matches the native CLI parity for these options ([HTPR-6125](https://app.hypertask.ai/detail/project-15/6125)).</Aside>

## Tasks commands

### hypertask tasks move

Move a task from one section to another.

```bash
hypertask tasks move <ticket> --section <section-name>
```

**Behavior:**

- If the task is archived, the command will fail with the error:
  >
  > "Archived tasks cannot move sections or change assignees"
  >
  This message clarifies that archived tasks are immutable for moves; attempt to restore the task first, or create a new task.

- You can also change assignees with:
  >
  > `hypertask tasks move <ticket> --assignee <user>`
  >
  For full options, run `hypertask tasks move --help`.

### hypertask comment react

Add an emoji reaction to a comment from the terminal.

```bash
hypertask comment react <ticket_number> <comment_id> --emoji <emoji>
```

**Behavior:**

- React to existing comments to acknowledge them without leaving a reply.
- Use a single emoji character (e.g., `👍`, `❤️`, `🔥`).
- Requires authentication via API key or session cookie.

### hypertask comment unreact

Remove an emoji reaction from a comment.

```bash
hypertask comment unreact <ticket_number> <comment_id> --emoji <emoji>
```

**Behavior:**

- Removes the specified reaction from a comment.
- Useful for correcting mis-typed acknowledgments.
- Requires authentication.

**Reactions tab (web UI):**

The web app provides a dedicated reactions tab for each comment, showing all reactions and the users who added them. The CLI complements this by enabling quick reactions from any terminal.

## Webhook commands

### hypertask webhook configure

Configure webhook events for an agent.

```bash
hypertask webhook configure --url <webhook-url> --events <events>
```

**Behavior:**

- `--url` (required): Target webhook URL to listen for notifications.
- `--events` (required): One or more space-separated webhook events.
- Provides immediate feedback indicating whether the configuration was accepted.

**Supported events:**

The latest production CLI now accepts the full set of 7 webhook events: `chat.message`, `created_bulk`, `task_updated`, `task_created`, `user_moved`, `board_updated`, and `agent_reconciled`.

**Example:**

```bash
hypertask webhook configure --url https://example.com/webhook --events "chat.message task_updated"
```

**Troubleshooting:**

- An invalid event string or a deprecated event will result in a rejection message.
- If you previously used a stale client-side event list that rejected all events, make sure your current CLI release includes the updated event metadata.

<Aside type="note">Webhook event validation had a stale client-side event list for some CLI releases, rejecting valid events like `chat.message`. The current production release now accepts the full set of 7 events, including `chat.message` ([HTPR-6114](https://app.hypertask.ai/detail/project-15/6114)).</Aside>

## Trusted CLI Release Gate (advisory, not a hard block)

### How release checks work

Hypertask uses a CI/CD parity gate to verify that CLI release behavior aligns with the production app, but it no longer blocks production on a mismatch. Changes are handled through:

- **Advisory warning when the CLI's latest appears to have updated**: The CLI now warns users during release checks when the published CLI version differs from production, but continues to allow the build.
- **Trusted version allowlist**: Trusted CLI versions must be in an allowlist; all others are treated as untrusted and receive advisory warnings.
- **Parity inventory validation**: A parity inventory task ensures that changes to CLI behavior are recognized and tracked.
- **Failure-tolerant npm lookup**: If an unrelated publish occurs or npm data drifts, the CLI shows a warning instead of failing.

### Node half release compatibility

When a change lands on the Node CLI half and is mapped straightforwardly to an htz binary behavior, the production build publishes after a passing Node parity test and an allowlist update. If the semantic difference is meaningful enough to break worker workflows, the change is handled through a separate Node-specific release and parity gating before matching to htz.

This advisory release check keeps Node CLI build iterations visible to users without halting production. Trusted versions remain vetted; all others are warned but not blocked.

### Worker behavior

Workers must not stop at an advisory warning about the CLI version. The advisory indicates that a newer or mismatched version is available, and a warning does not mean a regression with the change the worker just shipped.

It is the responsibility of the build or publish process to ensure the CLI behavior matches the expectations in the parity inventory and allowlist before marking a release as trusted.

## Trusted CLI version approval

Trusted CLI versions are approved through a manual review and pin-bump process:

1. The manager reviews each CLI release diff, comparing:
   - The npm tarball
   - Dependency changes
   - Published npm provenance
2. If the diff is clean and matches expectations, the manager opens a pin-bump pull request the same hour, updating the trusted version in the parity gate configuration.
3. The gate's trusted pin never tracks npm automatically; a new trusted version exists only after an explicit review and pin-bump.

This ensures the gate stays bounded to the version the team has inspected and approved.

### What is allowed to change before approval

For a CLI version to remain trusted:

- Node CLI behavior must map cleanly to the htz binary behavior (semantic parity).
- Dependency changes must not break worker workflows.
- New CLI commands or flags must be accompanied by documentation and intended use cases.
- Works intended for the Node-only half (to avoid regressions with htz) can proceed with limited trust.

Changes outside these bounds trigger advisory warnings and may be handled via dedicated Node-side releases.

## Trusted version allowlist

The trusted version allowlist captures CLI versions considered production-ready. When a new version becomes trusted:

1. A parity inventory task identifies behavior differences between the new version and the previous trusted version.
2. The allowlist is updated with the new version.
3. Advisory warnings are cleared; future builds will no longer show the warning.

CLI versions not in the allowlist receive advisory warnings but are not blocked.

### Notes and friction

- If build logs show an advisory warning, check that the parity inventory is up to date and that allowlist entries are correct.
- If production was blocked previously due to a mismatch, the Node half release was either pinned out of the blockage path or shipped with a separate trusted version.
- Unrelated npm publishes that do not match the Rust ptz signature or that represent small updates (e.g., documentation-only) surface a warning but do not stop the build.

## Claims and Parity Tests

The Hypertask CLI includes an automated parity test (`hypertask parity_test.py`) that validates end-to-end behavior against the documented CLI contract.

### What the parity test checks

The `hypertask parity_test.py` harness performs comprehensive comparison against the served Node implementation:

- **JSON schema verification** — Compares output against 30 read-only JSON schemas for list, create, and detail operations.
- **Authentication matrix** — Verifies correct response for each supported token flow (API key, session cookie, auth header combination).
- **Human-output parity** — Includes tests for `--human` (human-oriented label rendering) and human-oriented tables.
- **Negative case coverage** — Rejects unauthenticated access for operations that require authentication using the documented error contract.
- **Exit-code and finally output** — Validates that the installed htz CLI yields documented exit codes and fallback messages compared to the Node CLI.

<Aside type="note">The parity test ensures that any change to `hypertask list`, `hypertask get`, `hypertask create`, `hypertask update`, or any other command does not introduce regressions compared to the published contract.</Aside>

### Running the harness locally

```bash
# Quick check for recent merge
npx @hypertask/parity-test-cli@latest

# Custom path to the Node distribution
npx @hypertask/parity-test-cli@latest --node-dist /path/to/cli.tar.gz
```

### API and routing parity

The parity harness confirms that `hypertask` maps to the latest route contract supporting authenticated read-only flows. PR #20 includes six parity tests (cases) and coverage confirms:

- IndexedDB-backed fetch and rendering (no pings to upstream).
- Token-source precedence (API keys versus session cookies).
- 30 previously defined read-only JSON schemas.

These tests validate both positional params and flags against the server contract. All checks pass in local and live runs, confirming CLI behavior aligns with the documented contract.

<Aside type="tip">The CLI parity harness now also validates JSON diffs, auth matrix, negative cases, token-source precedence, and human output against the Node CI contract and passes locally and in live runs.</Aside>
