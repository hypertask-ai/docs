The Hypertask CLI (`htz`) lets you manage tasks, projects, comments, and notifications directly from your terminal. At v0.2.0, `htz` is the only official Hypertask CLI; the legacy Node CLI (`@hypertask/hypertask_cli`) has been retired and is no longer maintained.

## Migrate from legacy CLI

If you're currently using the Node CLI (`hypertask` or `@hypertask/hypertask_cli`), follow these steps to switch to htz:

| Node CLI command | htz command | Notes |
|------------------|------------|-------|
| `hypertask task create` | `htz task create` | Flags map 1:1 |
| `hypertask task list` | `htz task list` | Add filters with flags |
| `hypertask task get` | `htz task show` | `task show` is an alias for `task get` |
| `hypertask project list` | `htz project list` | Same behavior |
| `hypertask capabilities` | `htz capabilities` | Lists all available commands |
| `hypertask login` | `htz login` | Same authentication flow |

Most commands and flags work the same way. The main difference is that `htz` avoids the `--json` requirement for human-readable tables and prints a clean card-style output by default.

<Aside type="note">
**Old command aliases:** The Node CLI previously exposed `section` commands under `project section`. In htz, you run `section create` directly from the top level, without the `project` prefix.
</Aside>

### Example migration

Before:

```bash
hypertask task create \
  --project 15 \
  --title "Implement dark mode toggle"
```

After (same flags, different binary):

```bash
htz task create \
  --project 15 \
  --title "Implement dark mode toggle"
```

### Remove the Node CLI

Once you've verified htz works for your workflows, uninstall the Node package:

```bash
npm uninstall -g @hypertask/hypertask_cli
```

If you still have the legacy binary source locally, you can safely archive or delete it.

<Aside type="caution">
**Deprecated package:** The legacy Node CLI package `@hypertask/hypertask_cli` is deprecated and is no longer receiving bug fixes. Future features will only be available in htz.
</Aside>

## Authentication

<Steps>

1. **Login via browser** (recommended):

   ```bash
   htz login
   ```

   This opens your browser to authenticate and saves the token locally. After the `api.hypertask.ai` cutover, htz always routes login requests through the new API endpoint to avoid 404s and ensure reliable authentication.

2. **Login with a token** (for CI/headless environments):

   ```bash
   htz login --token <your-jwt-token>
   ```

3. **Check your auth status:**

   ```bash
   htz status
   ```

4. **Logout:**

   ```bash
   htz logout
   ```

</Steps>

<Aside type="tip">
Pass `<code>--token <jwt></code>` on any command to override the saved token for that call. You can also pass `<code>--api-url</code>` to point at a custom API endpoint.
</Aside>

## JWT expiry and auto-refresh ([HTPR-5797])</p>

<span class="label label--brand">Behavior change</span> The installed CLI now auto-refreshes saved JWTs before they expire and shows the exact UTC expiry date for older, non-rotating tokens. This prevents unexpected command failures due to expired credentials.

<Aside type="note">
Expiration handling uses the `exp` claim from the JWT. Refresh and expiry reporting are surfaced to CLI users via `login` and `status`, without exposing internal token algorithm or claim details.
</Aside>

## Exit Codes and Error Behavior</p>

The CLI uses exit codes so scripts and CI pipelines can reliably detect failures.

### Exit Codes</p>

| Code | Meaning |
|------|---------|
| `0` | Success |
| `1` | General runtime or API error (non-auth) |
| `4` | Authentication or authorization failure |
| `2` | Invalid usage â\x80\x94 unknown or misspelled subcommand / missing required argument |

<Aside type="caution">
Use `htz capabilities --json` in automation pipelines to discover whether a command supports JSON output without guessing, and rely on non-zero exit codes to detect failures.
</Aside>

## Transient Failures</p>

Bot-challenge 403s, rate limits, and certain gateway errors are retried automatically with exponential backoff instead of failing immediately. Starting from CLI 1.8.0:

- **Retried cases:** 403 (bot challenge), 408 (Request Timeout), 429 (Rate Limit), 500 (Internal Server Error), 502 (Bad Gateway), 503 (Service Unavailable), 504 (Gateway Timeout)
- **Backoff sequence:** retry attempts are spaced approximately 2 seconds, 10 seconds, and 30 seconds, then fail with a clear message

**Not retried:** 500 and bare network errors are intentionally not retried to avoid re-processing a write that has already succeeded, which could cause duplicates or unexpected side effects.

## Non-fatal Errors</p>

Starting from CLI 1.10.0, commands that encounter missing resources exit with a non-zero code and a clear error message instead of succeeding silently.

## CLI Configuration Persistence</p>

Environment variables `HT_TOKEN`, `HYPERTASKS_JWT_TOKEN`, and `HYPERTASKS_API_URL` can override your saved CLI configuration. Empty values in these variables now leave the saved settings intact, preserving your existing authentication and server URL for agent shells that run with empty exports. This prevents accidental config wipes and keeps long-running agent sessions properly authenticated.

```bash
# Agent shell with empty environment overrides retains CLI settings
EMPTY_TOKEN="" EMPTY_JWT_TOKEN="" EMPTY_API_URL="" ht agent start

# Previously, this would reset your settings to defaults
```

## CLI API Routing</p>

htz connects to the Hypertask API using a dedicated endpoint that is exempt from the Vercel bot challenge:

- **Default endpoint:** `https://api.hypertask.ai`
- **Routing:** CLI traffic is routed through `api.hypertask.ai`, not `app.hypertask.ai/v1` or other public-facing endpoints
- **Benefit:** Direct API access works reliably from VPS environments without intermittent 403s caused by bot-challenge checks

```bash
# htz automatically connects to the exempt API endpoint
htz task get HTPR-2992
htz status
```

<Aside type="tip">
If you need to use a custom API URL (for self-hosted instances), you can override it via `<code>--api-url</code>`. This overrides the default routing and should not be required for standard Hypertask.
</Aside>

## Commands</p>

### `capabilities` [list commands]
Lists all available commands and their descriptions. By default, `htz capabilities` emits a human-readable Markdown summary. Pass `--json` to get a complete machine-readable catalog for automation.

**Example - Markdown output (default):**

```bash
$ htz capabilities

# Hypertask CLI - Available Commands
- task create         Create a new task
- task list           List tasks with filters
- task show           Show task details
- project list        List projects
- login               Authenticate via browser or token
- status              Check auth status
- logout              Sign out
...
```

**Example - JSON output (for automation):**

```bash
$ htz capabilities --json | jq '.capabilities[] | {command, description}'
# Complete catalog with all commands, machine-readable for scripts
```

**Changes since v1.8.0 ([HTPR-5776]):** In previous versions, `htz capabilities` printed a larger 55 KB JSON document regardless of argument usage. Now, human-facing usage prints a compact Markdown summary. Agents that request `--json` receive the full machine-readable catalog.

---

### `labels list --project <ID>`
List labels scoped to a specific board/project. This replaces the previous behavior where `labels list --project <ID>` returned a global project list instead of board-specific labels.

**Example:**

```bash
$ htz labels list --project 15

# Board 15 Labels
- critical
- high-priority
- frontend
- backend
- qa
```

**Changes since v1.8.0 ([HTPR-5777]):** The command now returns board-specific labels instead of a global project list, aligning with board-scoped workflows. Additionally, output is formatted as Markdown instead of truncated JSON.
